# 聚聚星接入设计（v1）

## 目标

把“按共同时间顺序拼候选”升级为可解释的组局决策：每个方案明确说明谁能来、谁被时间或通勤挡住、哪些路线尚未确认，以及有什么可执行的修复方案。

## 边界

聚聚星继续负责登录、成员同意、地图路线、活动候选和 UI；MoonBit 核心只接收匿名成员 ID、时间窗、兴趣、路线分钟数与规则。核心不保存手机号、精确住址、地图密钥或聊天记录。

```
聚聚星填写偏好 -> 聚聚星云端聚合/路线估算 -> juju-planner-request/v1
                                                    -> MoonBit 决策内核
                                                    -> 推荐/取舍/拒绝理由/修复建议
                                                    -> 聚聚星投票与确认页
```

## 接口

请求样例见 [`examples/juju-planner-request.v1.json`](../examples/juju-planner-request.v1.json)。字段约定：

- `startMinute` / `endMinute` 是本地当天 0:00 起的分钟数；活动必须完整落入成员可用时间。
- `commuteMinutes[i]` 对应 `members[i]`；`null` 是**未知路线**，不能替换成很大的虚构数值。
- 默认规则是“至少两人 + 指定关键成员”；`requireEveryone: true` 时才启用全员必须到场。
- 所有 `id` 使用聚聚星内部的伪匿名成员 ID，不传联系方式。

`integration/juju-planner-contract.js` 是可在小程序/云函数侧运行的 CommonJS 正规化器。它先拦截不完整或错位的数据，防止把错误输入交给算法。

## 推荐呈现

页面不要只展示“第一名”。至少同时呈现：

1. **人最齐**：最多可确认参加者；
2. **最省心**：平均通勤最低；
3. **最合兴趣**：兴趣匹配最多；
4. **待确认**：路线未知的人数与补充入口；
5. **换个时间试试**：对被拒方案给出 ±30/60 分钟内确实可行的平移建议。

算法同时提供按分数排序的默认卡片和 Pareto 前沿：当一个方案人更多但路更远时，二者都会保留，避免一个不透明权重替用户做价值判断。

## 接入顺序

1. 在聚聚星云端从每位已同意成员收集真实时间窗，并在成员顺序固定后计算到每个候选地点的路线分钟数。
2. 用 `buildPlannerRequest` 生成并校验 v1 请求；数据不完整时只显示“待补充”，不作公平性结论。
3. 将 MoonBit JS 构建物封装进一个云函数/服务端适配层，返回 `DecisionReport`；小程序不运行地图和决策密钥。
4. 先用 10 个真实但脱敏的组局回放对比旧候选排序，再灰度展示“推荐理由”和投票结果。

当前仓库已完成第 2 步的数据契约和可验证的决策内核；第 3 步需要在聚聚星的云端部署环境中选择运行方式后再接入，不能仅靠前端文件假装已经上线。
